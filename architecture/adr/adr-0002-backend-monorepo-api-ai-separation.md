## 맥락과 문제 [필수]

`my-space` 백엔드는 마크다운 노트, RSS 피드, 관리 일정(공통 날짜 모델 3유형), 인앱 알림, `qpdf` PDF 조작 같은 빠른 응답(`NFR-003`)이 필수적인 트랜잭션 API와, 실시간 음성(STT/TTS)·텍스트 SSE 스트리밍 및 마크다운 문서 청킹·벡터 임베딩 인덱싱을 수행하는 `공간 › AI` 워크로드를 함께 다루어야 한다.

AI 스트리밍과 문서 임베딩 워커는 외부 LLM/음성 엔진 대기 시간이 길고 오디오·벡터 버퍼로 인한 메모리/CPU 변동폭이 크다. 단일 프로세스로 묶으면 AI 작업 부하나 장애가 노트 저장·일정 관리 API까지 지연시킬 위험이 있고, 반대로 Git 저장소까지 쪼개면 Prisma DB 스키마, RustFS 스토리지 클라이언트, Authelia 인증 가드가 중복된다. 장애 격리와 코드 재사용을 어떻게 동시에 달성할 것인가?

## 고려한 대안 [필수]

| 대안 | 장점 | 단점 | 결정 동인 충족 |
|---|---|---|---|
| **A. 단일 백엔드 모노레포(`my-space-backend`) 내 `apps/api`·`apps/ai` 독립 프로세스 분리 + `RabbitMQ` 비동기 인덱싱** | 프로세스·메모리 완전 격리. 노트 저장 시 큐 발행만으로 즉각 응답. `libs/common`·`libs/storage`로 스키마·인증 코드 100% 공유 | 배포 컨테이너가 2개(`api`, `ai`)가 되고 노트 저장 후 벡터 검색 반영까지 1~2초의 최종 일관성 지연이 있다 | 모두 충족 |
| B. 단일 NestJS 프로세스 내 모듈로 통합 | 배포 컨테이너가 1개여서 운영이 가장 단순하다 | 음성 합성·임베딩 연산 스파이크나 LLM 지연 시 이벤트 루프·메모리 경합이 발생해 일반 API 응답성(`NFR-003`)이 저하된다 | 불충족 (`AP-03`, `NFR-003`) |
| C. 별도 Git 저장소(Multi-repo)로 완전 분리 | 저장소 수준까지 물리적으로 분리된다 | Prisma 스키마와 인증 가드를 양쪽에 복제하거나 사설 npm 패키지로 배포해야 해서 1인 개발 유지보수 비용이 급증한다 | 불충족 (`AP-05`) |

## 결정 [필수]

**대안 A**를 채택한다. `my-space-backend`를 Nest CLI 표준 모노레포로 구성하여 일반 공간·도구 API와 Catch-up 스케줄러를 담당하는 **`api`(`apps/api`)**와 실시간 음성·텍스트 SSE 스트리밍 및 RAG 검색·인덱싱을 담당하는 **`ai`(`apps/ai`)**를 별도 컨테이너 프로세스로 분리하고, 노트 변경 시 **`RabbitMQ`**를 통해 비동기로 벡터 인덱싱을 수행하며, 공통 코드는 **`libs/common`과 `libs/storage`**로 공유한다.

## 결과 [필수]

- **좋아지는 점**:
  - `ai` 서버에서 무거운 음성 합성이나 대량 문서 재인덱싱이 돌아가거나 외부 LLM이 지연되어도 `api` 서버의 노트·피드·관리·PDF 기능은 영향을 받지 않는다.
  - 홈랩 자원 절약(`Scale to 0`)이 필요할 때 `ai` 컨테이너만 일시 중지하고도 기본 공간과 도구를 정상 운영할 수 있다.
- **나빠지는 점과 트레이드오프**:
  - 노트를 저장한 직후 `RabbitMQ` → `ai` 워커 → `Qdrant` 색인이 완료되기까지 수 초간의 비동기 지연(Eventual Consistency)이 존재한다.
  - 빌드 및 배포 파이프라인에서 `api`와 `ai` 두 아티팩트를 관리해야 한다.
- **후속 작업**:
  - [ARC-004 컨테이너와 주요 컴포넌트](../arc-004-containers-components.md)에 `api`, `ai`, `RabbitMQ`, `Qdrant` 역할 및 통신 정의
