# ADR-0005 인앱 알림함 우선 저장 및 외부 알림 채널(Slack Webhook) 어댑터 추상화

## 맥락과 문제 [필수]

`공간 › 관리`의 일정이 알림 기준일(`D-7`, `D-3`, `D-1`, `D-Day` 등)에 도달하면 사용자에게 지체 없이 알려야 한다(`REQ-010`).

1차 외부 알림 수단으로는 `Slack Incoming Webhook`을 사용하지만, 향후 Discord, Telegram, 이메일, 웹 푸시 등으로 채널이 변경되거나 추가될 수 있다([PRD-001 제약과 가정](../../product/prd-001-product-overview.md#제약과-가정-선택)). 또한 외부 Slack 웹훅 URL이 일시적으로 오류를 반환하거나 설정되지 않은 상태에서도 사용자가 워크스페이스에 접속했을 때 상단바 알림함과 홈 대시보드 브리핑(`REQ-002`)에서 누락 없이 알림을 확인하고 해당 일정으로 바로 이동할 수 있어야 한다. 알림 생성과 외부 발송을 어떻게 분리할 것인가?

## 결정 동인 [필수]

| 동인 | 출처 |
|---|---|
| 외부 알림 채널이 바뀌거나 추가되어도 일정 판별·Catch-up 도메인 로직을 수정하지 않아야 한다 | [PRD-001 제약과 가정](../../product/prd-001-product-overview.md#제약과-가정-선택), [ARC-002 AP-04](../arc-002-principles-constraints.md), `REQ-010` |
| 외부 웹훅 발송이 실패하더라도 인앱 알림함과 홈 대시보드 브리핑에는 알림이 100% 남아 있어야 한다 | `REQ-002`, `REQ-009`, [PRD-006 NFR-004](../../product/prd-006-nfr.md) |

## 고려한 대안 [필수]

| 대안 | 장점 | 단점 | 결정 동인 충족 |
|---|---|---|---|
| **A. `PostgreSQL` 인앱 알림함 우선 기록(Outbox 역할 겸용) + `NotificationChannel` 포트/어댑터 인터페이스를 통한 비동기 외부 발송(1차: `SlackWebhookAdapter`)** | 외부 장애와 무관하게 인앱 알림 100% 보존. 새 채널 추가 시 어댑터 클래스만 추가하면 됨. 발송 성공/실패 상태 추적 가능 | 알림 엔티티와 채널 어댑터 인터페이스를 설계해야 한다 | 모두 충족 |
| B. 스케줄러에서 Slack Webhook HTTP 호출만 직접 수행 (DB 알림 테이블 미보유) | 테이블이 하나 줄어든다 | 상단바 인앱 알림함(`SCR-002`, `REQ-002`)을 구현할 수 없고, Slack 장애 시 알림이 영구 유실되며, 도메인 코드가 Slack 포맷에 강결합된다 | 불충족 (`REQ-002`, `REQ-010` 실패) |

## 결정 [필수]

**대안 A**를 채택한다. Catch-up 및 일정 스케줄러가 도래 일정을 감지하면 먼저 **`PostgreSQL`의 인앱 알림 테이블에 알림 레코드(읽음 상태, 대상 화면 경로, 외부 발송 상태 포함)를 생성**하고, 이어서 **`NotificationChannel` 인터페이스**를 구현한 어댑터(1차: `SlackWebhookAdapter`)를 비동기로 호출해 외부 메신저로 발송한다.

## 결과 [필수]

- **좋아지는 점**:
  - Slack 웹훅이 실패하거나 오프라인이더라도 사용자는 상단바 알림 아이콘과 홈 대시보드에서 모든 도래 일정을 확인할 수 있다.
  - 추후 다른 메신저로 전환할 때 비즈니스 로직 변경 없이 어댑터만 교체·추가할 수 있다.
- **나빠지는 점과 트레이드오프**:
  - 외부 발송 실패 시 재시도 횟수 상한과 발송 상태(`PENDING`, `SENT`, `FAILED`) 컬럼을 알림 레코드에서 함께 관리해야 한다.
- **후속 작업**:
  - [ARC-004 컨테이너와 주요 컴포넌트](../arc-004-containers-components.md)의 `Catchup & NotificationModule`에 반영
