# INF-011 인프라 운영 절차

| 절차 | 시작 조건 | 실행 권한 |
|---|---|---|
| [RB-001 재기동 점검](#rb-001) | 호스트 기동, API 불가, Catch-up 지연 | 클러스터 조회·운영 점검 계정 |
| [RB-002 원본 복구](#rb-002) | PVC 손실·잘못된 삭제·원본 불일치 또는 격리 복원 훈련 | 백업 판독·복호화 및 격리 DB·버킷 복원 권한, 운영 전환 권한 |
| [RB-003 파생 색인 재생성](#rb-003) | 검색·RAG 지연, 큐·색인 소실, 원본 복원 후 | 대상별 api·ai 재처리와 색인 전환 권한 |
| [RB-004 배포 롤백](#rb-004) | 배포 직후 보호 경로나 저장 회귀 | 인프라 Git 변경·Argo CD 동기화 권한 |

운영자는 실행 전 클러스터 컨텍스트, 환경, 실행 시각, 배포 Git 리비전을 기록한다. 아래 조회는 홈랩 선언을 기준으로 하며, 변경 작업은 [접근 제어](inf-003-network-access.md)와 [GitOps 배포 절차](inf-005-ci-cd.md)를 따른다. 첫 v2 훈련에서 절차별 시작·종료 시각과 결과를 남겨 소요 시간을 산정한다.

### RB-001

**재기동 후 원본과 스케줄 확인**

1. 다음 조회로 노드 Ready, 원래 PVC의 Bound 상태와 연결 볼륨, `qdrant` 포함 인프라 파드와 실제 앱 복제 수, Argo CD 동기화 상태를 확인한다. 호스트·WSL2·포트 연결 복구는 [호스트 재기동 가이드](../../homelab-infra/docs/host-reboot-recovery-guide.md)의 1~2단계를 따르되, v2 헬스·인증 검증은 `api.homelab.local`이 아닌 동일 출처 `https://my-space.homelab.local` 기준으로 수행한다.

   ```sh
   kubectl config current-context
   kubectl get nodes
   kubectl -n infra get pvc postgres-pvc rustfs-pvc
   kubectl -n infra get statefulset qdrant
   kubectl -n infra get pods
   kubectl -n apps get deploy,pods
   kubectl -n argocd get applications
   ```

2. PostgreSQL과 RustFS의 준비 상태를 확인하고, 주 사용자 점검 계정으로 동일 출처 보호 API를 통해 기동 전 기록한 기준 노트의 현재·이전 리비전과 첨부를 읽는다. 방문자의 개인 데이터 접근은 거부되어야 한다. 앱이 빈 DB나 새 볼륨을 보거나 기준 객체가 누락되면 쓰기·GC를 즉시 막고 RB-002로 이동한다.
3. 호스트 기동, API Ready, 첫 Catch-up 개시, 보정 완료 시각을 대조한다. 작업별 체크포인트와 RSS·일정·인앱 알림의 중복·누락을 확인한다. 실패 시 체크포인트를 앞당기지 않고 마지막 커밋과 실행권을 확인한 뒤 멱등 재개한다. 외부 발송 성공 여부가 불명확하면 발송 기록을 대조한 후 재시도한다. [NFR-004 복구 목표](../product/prd-006-nfr.md#복구-목표-선택) · [스케줄 규칙](../backend/be-005-domain-model-rules.md)
4. 기존 데이터·권한, 스케줄 결과, 서비스별 Ready가 일치하면 재기동 점검을 종료한다. 검색·RAG만 뒤처졌으면 원본을 보존한 채 RB-003을 진행한다.

### RB-002

**손상 시점 판별과 격리 복원**

1. 실제 사고면 Argo CD 자동 동기화 해제(`syncPolicy: null`)·앱 축소·파드 `0`건 종료 확인으로 유입과 모든 쓰기·GC·외부 발송을 중지한다. 원래 볼륨과 사고 시점의 상태를 보존한다. 볼륨 재연결만으로 정상화되면 RB-001로 검증한다. 손상이 확인되면 마지막 정상 세트와 그 뒤 유실 가능 구간을 기록한다.
2. [INF-009](inf-009-backup-recovery.md)의 세트를 별도 매체에서 읽어 복호화하고 덤프·객체 사본의 체크섬을 확인한다. 격리 환경은 운영 클러스터와 물리적으로 분리된 **로컬 임시 Docker(`postgres:18` + `rustfs`)**를 표준으로 사용하며(클러스터 내 격리 시 운영과 별도 임시 DB명·버킷명 강제), 원래 객체 키로 두 버킷을 복원하고 같은 세트의 DB를 호환 버전에 복원한다. 앱 시작 전에 운영 자격 증명, 운영 DB·큐, 공개 유입, 외부 LLM·Slack·RSS 연결을 차단한다. 스케줄러·발송·색인 워커는 검증할 때까지 중지한다.
3. DB의 모든 보존 리비전과 첨부 연결에서 객체 목록을 만들어 복원본의 키·크기·체크섬과 대조한다. 격리된 api로 과거 리비전·첨부 읽기, 삭제 문서 차단, 소유권 격리, 피드·일정·AI 이력 및 알림·체크포인트를 확인한다. 누락·손상이 있으면 해당 세트를 탈락시키고 더 이른 완전 세트를 빈 대상에 다시 복원한다.
4. 훈련에서는 격리 환경에서 RB-003과 Catch-up을 시험하고 외부 전달은 테스트 대역으로 받는다. 실제 복귀 시에는 복원 지점 이후 삭제·권한 변경과 이미 전달한 외부 알림을 남아 있는 신뢰할 수 있는 기록과 대조한다. 확인되지 않은 항목은 공개·발송을 보류한다. 운영자가 예상 손실과 원본 검증 결과를 확인한 뒤 이전 쓰기 경로를 차단한 상태에서 새 DB·버킷을 함께 연결한다.
5. 보호 경로 읽기를 먼저 확인하고 한쪽 환경에서만 쓰기를 재개한다. 색인과 외부 발송은 각 검증이 끝나는 대로 재개한다. 전환 후 새 쓰기가 있으면 단순 역전환 시 그 쓰기를 잃을 수 있다. 문제가 생기면 유입을 다시 닫고 변경분을 보존한 뒤 복귀 지점을 결정한다. 훈련 기록에는 원본 사용 가능 시각과 검색·RAG 정상화 시각을 따로 남긴다.

### RB-003

**OpenSearch·Qdrant 재생성과 큐 손실 대응**

1. 원본 읽기, 대상별 Outbox 상태, RabbitMQ 발행 확인·소비 상태, 적용 리비전을 비교한다. 잠깐의 지연이면 실패한 **대상만** 기존 재시도·실행권 회수 절차로 재개한다. 원본 누락이면 RB-002로 이동한다. [BR-004](../backend/be-005-domain-model-rules.md)
2. 색인 전체나 큐가 유실됐으면(큐 강제 비우기 포함) 전체 원본을 대조한다. 빈 색인에 대해 예전 `SENT`나 ENT-019의 이전 적용 리비전을 그대로 성공으로 취급하면 문서를 건너뛴다. 원래 타깃용 워커를 정지·배출하고 새 대상의 적용 기록을 분리하거나 재초기화한다. 이전 인덱스와 적용 기록은 복귀에 대비해 보존한다. [물리 모델](../backend/be-006-database-erd.md)
3. api는 현재 소유자·리비전·삭제 상태를 읽어 OpenSearch를 채우고, ai 작업은 RabbitMQ를 통해 전달한다. ai는 DB와 RustFS를 대조하고 해당 모델·컬렉션의 Qdrant를 재생성한다. *(이 전체 재색인·`ENT-019` 재초기화 실행 수단인 관리용 CLI 또는 일회성 Job은 v2 구현 시 제공할 운영 도구 요구사항이다.)* 스캔 시작 이후 변경은 Outbox로 따라잡고 전환 직전 잠시 쓰기를 멈춰 최종 차이를 대조한다. 구버전 이벤트·중복·삭제 표식은 [ADR-0008](../architecture/adr/adr-0008-note-write-consistency.md)의 순서·멱등 규칙으로 처리한다.
4. 소유자·현재 리비전별 누락, 구버전·삭제 결과 노출, 타 사용자 검색·RAG 결과가 모두 0인지 확인한다. 실패·대기 작업과 대상별 적용 기록까지 맞으면 검증한 대상부터 전환하고 쓰기를 재개한다. 실패하면 원본 쓰기를 재개하되 해당 검색 경로는 제한한다. 이전 대상 복귀도 현재 DB의 삭제·권한·리비전 검증을 통과한 경우에만 허용한다.

### RB-004

**배포 롤백과 데이터 호환성 확인**

1. 이 절차는 **v2 운영 중 릴리스 간 회귀 복귀**에 적용한다(v1→v2 최초 일괄 컷오버 실패 시에는 백업 복원인 [RB-002](#rb-002)로 복구한다). 회귀 발생 시점의 Git 리비전·실행 digest와 직전 정상 조합을 기록한다. API 보호 경로, DB 스키마·객체 형식, Secret 참조와 게이트웨이 설정이 이전 이미지와 호환되는지 확인한다.
2. 호환되면 [INF-005](inf-005-ci-cd.md)에 따라 검증된 digest와 설정을 Git에서 함께 복귀시키고 Argo CD 동기화를 확인한다(`argocd app rollback` 단독 실행 대신 Git 상태 복귀). 호환되지 않으면 쓰기를 중단하고 변경 후 데이터를 보존한다. 이전 원본이 필요한 경우 RB-002에서 복원 이후 유실 범위를 먼저 판단한다.
3. 원하는 digest와 실제 이미지, Ready, 동일 출처 접근, 주 사용자 조회·저장, 방문자 거부를 확인한다. 확인에 실패하면 쓰기 유입을 닫고 직전 정상 조합과 원본을 다시 대조한다. [v2 컷오버 가이드](../../homelab-infra/docs/my-space-v2-infra-guide.md)

### RB-005

**백업 실패와 관측 공백 점검**

1. 백업 실패 시 마지막 유효 세트는 보존하고 실패한 세트는 복원 후보에서 제외한다. 독립 매체 연결·공간·암호화 키 접근·쓰기 중단 구간을 확인한 뒤 [INF-009](inf-009-backup-recovery.md)의 전 과정을 새 ID로 다시 수행한다. 완전 세트가 확보될 때까지 손실 가능 구간을 기록하고 데이터 변경을 수반하는 배포를 보류한다.
2. 관측 공백이면 먼저 RB-001의 직접 조회와 `kubectl logs`로 앱 장애와 수집기 장애를 구분한다(RustFS 장애 시 Loki도 함께 중단될 수 있음에 유의). Prometheus 대상, Alloy·Loki 상태, Grafana 데이터 소스와 v2 서비스 라벨(`my-space-api`, `my-space-ai`)을 차례로 확인한다. 운영 채널 수신 실패는 수집 상태와 별도로 점검한다.
3. 새 샘플·비민감 시험 로그의 조회와 경보 발생·해제 통지 수신을 확인한다. 설정을 바꾼 뒤 신호가 사라지면 관측 설정만 직전 Git 리비전으로 복귀한다. 누락된 기간과 마지막 정상 시각을 운영 기록에 남긴다. [INF-010](inf-010-observability.md)
